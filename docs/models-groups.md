# 模型与分组

模型决定能力，分组决定线路和策略。大多数接入问题都可以从这两个维度拆开排查。

## 模型是什么

模型名是请求里的 `model` 字段，例如：

```json
{
  "model": "<MODEL_ID>",
  "messages": [
    { "role": "user", "content": "你好" }
  ]
}
```

这里的 `<MODEL_ID>` 必须换成 DouDi 控制台当前显示的完整模型名。模型是否可用取决于控制台当前配置、账户权限、Key 分组和上游状态。不要只根据其他平台教程复制模型名。

## 分组是什么

分组是一组线路和价格策略。你可以把它理解为“这个 Key 可以走哪些线路”。同一个模型在不同分组下可能有不同倍率、容量和可用性。

常见选择方式：

| 需求 | 建议 |
| --- | --- |
| 第一次测试 | 使用默认或自动分组 |
| 稳定批量调用 | 联系运营确认专用分组 |
| 成本敏感任务 | 先看价格页，再用低成本分组压测 |
| 高价值请求 | 选择更稳的线路，不只看最低价格 |

## 请求排查顺序

当请求失败、变慢或命中非预期模型时，按这个顺序看：

1. 请求日志里的 `request_id`。
2. 请求使用的模型名。
3. Key 绑定的分组。
4. 实际命中的渠道。
5. 上游返回的状态码和错误内容。
6. 是否发生失败切换或重试。

## 注意事项

- 价格页和模型广场是当前事实来源。
- 分组显示名可能调整，不应把显示名当成稳定接口契约。
- 下游系统需要稳定接入时，应保存自己的模型白名单，并在变更前做灰度测试。
